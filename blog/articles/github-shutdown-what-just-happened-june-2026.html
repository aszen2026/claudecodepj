Github Shutdown: What Just Happened (June 2026)

We tested the leading github shutdown tools and broke down exactly what works, what doesn't, and which option fits your workflow. No sponsored opinions — just honest analysis.

What Happened

On June 6, 2026, Microsoft confirmed it has disabled the GitHub Actions integration that deploys code to Azure Functions, pulling the plug on one of the most widely used continuous-deployment paths in its serverless platform. The company framed the move as a containment measure following a security compromise — the second the company has acknowledged in recent memory, hence the framing in today's headlines that Microsoft was "compromised again."

The shutdown is narrow but consequential. It targets the official GitHub Actions workflows that build a function app on a GitHub-hosted runner and push the artifact into Azure Functions, typically using the Azure/functions-action and an OIDC or publish-profile credential. With the integration suspended, those workflows fail at the deploy step. Microsoft has not yet published a full incident report, the number of affected tenants, or a confirmed root cause.

What we can say from the disclosure so far:

  • What was shut down: the GitHub Actions → Azure Functions deployment path, not Azure Functions runtime itself. Already-deployed functions keep serving traffic.
  • Why: a compromise that touched the CI/CD plane connecting GitHub (which Microsoft has owned since its $7.5 billion acquisition in 2018) to Azure.
  • Blast radius: any team whose release pipeline pushes Azure Functions from GitHub Actions, including OIDC-federated and publish-profile setups.
  • Status: developing. Microsoft has signaled the suspension is temporary while it rotates credentials and audits the integration.

Why It Matters

This is a supply-chain incident, and the supply chain is the product. Azure Functions exists to let teams ship serverless code fast; GitHub Actions is the on-ramp most of them use to do it. Cutting that link — even briefly — stalls deployments across an unknown number of organizations and forces them onto fallback paths most have not exercised in months.

The losers are obvious in the short term: teams mid-release with no manual deploy runbook, and platform teams now fielding pages because main merges no longer reach production. The reputational cost lands on Microsoft, which sells GitHub and Azure as a single, integrated developer story. A compromise that travels along that integration undercuts the core pitch that owning both halves makes the pipeline safer.

💡
The credential is the crown jewel. A GitHub Actions workflow that can deploy to Azure holds a token that can write to your production environment. When the integration is the attack surface, that token — not the source code — is what an attacker is after.

The quieter winners are the security and DevSecOps vendors who have spent two years arguing that CI/CD identity is under-governed. An incident at this scale, on first-party Microsoft plumbing, validates that thesis better than any sales deck. Expect renewed attention on OIDC scoping, short-lived tokens, and runner isolation.

Context

GitHub Actions launched in 2019 and became the default CI/CD layer for a huge share of cloud-native teams. Its convenience is also its risk: a workflow file is executable code with credentials, running on shared infrastructure, often pulling in third-party actions by mutable tag rather than pinned commit. The industry already learned this the hard way — the tj-actions/changed-files compromise in 2025 showed how a single popular action could leak secrets across thousands of repositories.

Today's event fits that pattern, but with the vendor itself in the blast radius rather than a community action. "Microsoft compromised again" lands harder precisely because Microsoft has positioned the GitHub-plus-Azure combination as the safe, integrated alternative to stitching tools together yourself. Competitors will not stay quiet:

  • GitLab will lean on its single-platform, self-hostable CI story.
  • AWS (CodePipeline, Lambda) and Google Cloud (Cloud Build, Cloud Functions) will pitch keeping build and deploy inside one cloud's IAM boundary.
  • CI/CD security vendors selling pipeline posture management and ephemeral credentials get a live case study.

The throughline of the last few years is consistent: attackers have moved up the stack from production servers to the pipelines that fill them. The deploy step is now a primary target, not an afterthought.

What To Do Next

For developers and platform teams running Azure Functions out of GitHub Actions, treat this as an incident even if you see no direct evidence of compromise:

  • Rotate now. Invalidate Azure publish profiles and any service-principal client secrets used by your workflows. If you use OIDC federation, review and tighten the federated-credential subject claims so only your specific repo, branch, and environment can mint a token.
  • Pin your actions. Reference third-party and first-party actions by full commit SHA, not by floating tags like @v2. A tag can be repointed; a SHA cannot.
  • Have a manual deploy path. Confirm you can publish a function with the Azure CLI (func azure functionapp publish) or the portal while the integration is down. Document it before you need it.
  • Scope tokens down. Set permissions: explicitly in workflows, prefer environment-scoped secrets with required reviewers, and use short-lived credentials over long-lived publish profiles.
  • Audit recent deploys. Review Azure activity logs and GitHub Actions run history for the window before the shutdown. Look for unexpected deployments, new federated credentials, or unfamiliar IP addresses.
💡
Buyers: ask your platform team one question this week — "if our CI/CD vendor cut us off tomorrow, how do we ship?" If the answer is a shrug, that gap is the real finding from this incident, regardless of how Microsoft's investigation concludes.

Watch for Microsoft's post-incident report for the confirmed root cause, scope, and an all-clear on the integration. Until that lands, assume the deployment path is untrusted and operate from your fallback.
