What Happened

On June 3, 2026, two tightly related packages landed on GitHub that point to the same idea: running a real Python interpreter inside a locked-down sandbox so that AI agents can execute the code they generate without touching the host system. The releases are micropython-wasm 0.1a1, published under Simon Willison's account (simonw/micropython-wasm), and datasette-agent-micropython 0.1a0, published under the Datasette organization (datasette/datasette-agent-micropython).

Both are explicitly pre-release alphas. The version strings tell the story plainly: 0.1a1 and 0.1a0 are first-week, "expect breakage" software, not production builds. There is no pricing, no funding announcement, and no SLA attached — these are open-source artifacts published as GitHub release tags.

  • micropython-wasm 0.1a1 — MicroPython, the lean reimplementation of Python 3 originally built for microcontrollers, compiled to WebAssembly. That makes a small, fast-starting Python runtime that can execute inside a browser tab or any WASM host.
  • datasette-agent-micropython 0.1a0 — a Datasette plugin that wires that WASM runtime in as an execution backend for an agent, so model-generated Python can run against Datasette data in a constrained environment.

The shared author and the shared June 3 timing are the key facts. One package is the engine (Python-in-WASM); the other is the harness (an agent that uses the engine inside Datasette).

💡
Why MicroPython and not CPython? Full CPython compiled to WASM (the Pyodide approach) is large and slow to start. MicroPython's whole reason for existing is to be tiny. As a WASM module it boots fast and carries a minimal surface area — which is exactly what you want when you're going to throw untrusted, model-written code at it repeatedly.

Why It Matters

The unsolved problem in agent tooling right now is not "can the model write code" — it's "where do you run the code safely." Most agent stacks today reach for a full container, a remote sandbox service, or a subprocess with the security turned off. Each option is heavy, adds latency, or adds a bill.

A MicroPython-WASM sandbox changes the trade-offs:

  • Isolation by default. WebAssembly has no filesystem, network, or syscalls unless the host explicitly grants them. An agent that runs Python inside WASM can't accidentally read your environment variables or shell out — the capability simply isn't there.
  • It can run client-side. Because the runtime is WASM, the execution can happen in the user's browser rather than on a server you pay for and have to lock down. That removes a class of infrastructure cost and a class of attack surface at once.
  • Datasette is the proving ground. Datasette is a widely used tool for publishing and exploring data through a web UI. Pairing an agent with a sandboxed runtime there means non-engineers could ask questions and have generated Python execute against the data safely.

Who benefits: developers building agent features who don't want to operate a sandbox service, and teams nervous about giving an LLM a real shell. Who feels pressure: hosted code-execution vendors whose pitch is "we run agent code safely for you," if a free, embeddable, client-side option becomes good enough for common cases.

Context

This fits a clear arc in the Python-in-the-browser story. Pyodide established that you could run scientific Python in WASM, but at a heavy download and startup cost. MicroPython has been steadily extending beyond microcontrollers, and a WASM target is the logical next host. What's new here is the framing: not "Python in the browser for notebooks," but "Python in the browser as an agent execution sandbox."

It also fits Simon Willison's own track record. Datasette, the llm CLI, and his plugin ecosystem have consistently pushed small, composable tools for working with data and language models. A WASM runtime plus a Datasette agent plugin is the same playbook: ship the primitive (micropython-wasm) and a concrete consumer of it (datasette-agent-micropython) in the same breath, so people can see why the primitive exists.

💡
Read the version numbers as a roadmap, not a product. A 0.1a0 plugin is a working sketch. The valuable signal isn't "use this in production today" — it's "the sandboxed-agent-execution pattern now has a reference implementation you can read."

What To Do Next

Concrete steps depending on who you are:

  • Developers building agents: Clone micropython-wasm and try running a snippet of model-generated Python through it. Measure cold-start time and confirm what's reachable from inside the sandbox — that tells you whether it can replace a heavier container step in your stack.
  • Datasette users: Install datasette-agent-micropython 0.1a0 in a throwaway instance against non-sensitive data. Treat it as evaluation, not deployment — pin the exact alpha version and expect the API to shift.
  • Teams evaluating sandbox vendors: Add "client-side WASM execution" as a column in your comparison. Even at alpha, it reframes the build-vs-buy question for sandboxed code execution.
  • Everyone: Watch the next tags on both repos. The jump from 0.1a to a first stable 0.1 — and whether more datasette-agent-* plugins appear — will show whether this is a one-off experiment or the start of a pattern.
